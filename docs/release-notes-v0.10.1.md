# ganttly v0.10.1 — 关键路径算法修复

> v0.10.0 之后的修复版:彻底重做"显示关键路径"的算法输入与语义——摘要任务不再以工作量冒充工期进入路径计算、四种依赖类型(FS/SS/FF/SF)全部按真实语义参与、手动拖期的任务回归关键路径。**开启关键路径后,所有存量项目的标红结果都会变化——这正是修复目的。**

🎨 **在线 demo**:https://chiangzg.github.io/ganttly/

---

## 修了什么

### 1. 摘要任务把"工作量"当"工期"喂给算法(主犯)

汇总任务的工期是**子任务工期求和**(工作量概念),而它的时间跨度通常远小于这个和。旧算法却把摘要当成一个普通任务塞进关键路径计算——摘要工作量越大,项目结束日被虚推得越远。真实项目实测:某分组 18 个子任务工期求和 146 个工作日,真实跨度只有 46 天,算法据此把项目结束日推到了三个多月后,导致**所有真实的最晚工作链都背上几十天幻影浮动、一条都不标红**;用户看到的红条是约束钉死的旧任务和一个"组内全不红"的红摘要条。

修复:**摘要任务退出路径计算**,只算叶子任务(里程碑视为叶子);摘要条的红由"是否包含关键叶子后代"派生——组红则组红,组内无红则组不红。

### 2. 四种依赖类型被当 FS 算

UI 支持完成→开始(FS)/开始→开始(SS)/完成→完成(FF)/开始→完成(SF)四种前置关系,自动重排引擎也按四种语义正确维持排程,但关键路径算法从不读取依赖类型、一律按 FS(前驱完成后才开始)计算——两边自相矛盾。构造 `A(10天) ←SS+2天— B(2天)` 即可让路径整体反转:A 明明决定结束日,旧算法却判 B 关键。

修复:四种语义全部进入正/反向计算,工作日步进与调度引擎完全一致;反向推导同样按类型镜像,SS/SF 场景下前驱的截止上限封顶于项目结束日。

### 3. 手动拖期的任务被算法无视

旧算法里,有依赖的任务只看"前驱允许它什么时候开始",完全无视你实际把它拖到了哪——拖晚三周也不红;反之,排得早的违约任务却占了便宜。修复后采用与 MS Project 一致的"按实际排程锚定":**你画在哪天,算法就认哪天**——手动拖期的任务继续驱动项目结束日并标红;违约提前的仍被网络拉回(不奖励违约)。

### 一并调整

- 任务表"关键路径"快捷筛选与画布高亮改用**同一份计算**,此前两者输入不同、结果可能对不上
- 任务抽屉的依赖候选**不再出现摘要任务**;摘要任务的依赖区显示提示(存量摘要级依赖数据无损保留,只是不参与路径计算)
- 约束任务(必须完成于/不得晚于)浮动为零而恒红,是标准 CPM 语义,本版保留
